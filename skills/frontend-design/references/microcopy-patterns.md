# UX Microcopy Patterns (Real, Not Placeholder)

> **Why this matters.** The #1 tell that UI was generated by AI is placeholder text
> ("Lorem ipsum", "Fast / Reliable / Secure", "Get Started"). Gummble MCP charges
> $9/mo specifically because it exposes *searchable, real* UX microcopy — empty
> states, validation errors, onboarding, and paywall copy written by real product
> teams. This reference gives you that same edge: write microcopy like a product
> team shipped it, never like a template filled it in.

**Rule:** NEVER ship `Lorem ipsum`, `TBD`, `Coming soon`, or generic triads
(`Fast. Reliable. Secure.`). Every string must read as if a real product team
wrote it for a real user in a real moment.

---

## 1. Empty States

Empty states are a *feature*, not a bug. They teach the user what the product
does and give them a next step.

| Context | Bad (placeholder) | Good (real) |
|---|---|---|
| No projects | "No items found." | "Nothing here yet. Create your first project and it'll show up right here." |
| No search results | "0 results." | "No matches for “{query}”. Try a different keyword or clear your filters." |
| Empty inbox | "Inbox empty." | "You're all caught up. New messages will land here." |
| No notifications | "No notifications." | "All quiet. We'll ping you when something needs your attention." |

**Structure:** (1) Acknowledge the state, (2) explain *why* it's empty, (3) offer
a single clear next action. Always pair with a primary CTA button, never just text.

---

## 2. Validation & Error Messages

Errors should say **what happened**, **why**, and **how to fix it** — in that order.
Never blame the user; never show raw tech jargon.

| Field | Bad | Good |
|---|---|---|
| Email | "Invalid email." | "That email doesn't look right — double-check for typos." |
| Password (short) | "Password too short." | "Use at least 8 characters. Longer is safer." |
| Password (mismatch) | "Passwords don't match." | "Those passwords don't match. Give it another try." |
| Required field | "This field is required." | "Please add your email so we can reach you." |
| Card declined | "Payment failed." | "Your card was declined. Try another card or contact your bank." |
| Network error | "Error 500." | "Something went wrong on our end. Please try again in a moment." |

**Tone:** human, specific, actionable. No "oops", no "something went wrong" without
a next step, no stack traces, no HTTP status codes shown to end users.

---

## 3. Loading & Progress

Loading is where trust is built or broken. Tell the user *what* is happening.

| Context | Bad | Good |
|---|---|---|
| Generic spinner | "Loading…" | "Fetching your projects…" |
| Upload | "Uploading…" | "Uploading 3 files — 40% done." |
| Processing | "Working…" | "Generating your report. This usually takes under a minute." |
| Long operation | "Please wait." | "Still on it — this can take up to 2 minutes. We'll let you know when it's ready." |

**Rule:** pair the spinner with a verb + object. If it takes >5s, add a progress
indicator or an estimated time. Never leave a bare spinner with no context.

---

## 4. Onboarding & First-Run

Onboarding microcopy should reduce friction and build confidence, not overwhelm.

- **Welcome:** "Welcome to {product}. Let's get you set up in under 2 minutes."
- **Benefit-first:** lead with the outcome ("Track every dollar"), not the feature.
- **Skip affordance:** always offer "Skip for now" — never trap the user.
- **Progress:** "Step 2 of 3" + a clear "Back" affordance.
- **Social proof:** "Join 12,000+ teams already using {product}."

---

## 5. Paywall & Upgrade

Upsell copy must be specific about *what you get*, never guilt-trippy.

| Bad | Good |
|---|---|
| "Upgrade to unlock." | "Free plan includes 3 projects. Upgrade to Pro for unlimited projects, priority support, and advanced analytics." |
| "Buy now!" | "Start your 14-day free trial — no credit card required." |
| "Premium features." | "Pro adds team roles, audit logs, and SSO." |

**Rule:** state the concrete delta between plans. Lead with the free trial or a
clear price anchor. Never hide the price.

---

## 6. Confirmation & Success

Confirmations close the loop and reinforce the action.

| Context | Bad | Good |
|---|---|---|
| Save | "Saved." | "Changes saved. Your team will see them immediately." |
| Send | "Sent." | "Email sent to {name}. They'll get it within a few minutes." |
| Delete | "Deleted." | "Project deleted. You can restore it from Trash within 30 days." |
| Publish | "Published." | "Your page is live at {url}." |

**Rule:** always confirm *what* happened and, when relevant, *what happens next*.

---

## 7. Destructive Actions (Confirmation Dialogs)

Be explicit about irreversibility. The button label should name the action.

- **Title:** "Delete this project?"
- **Body:** "This permanently removes “{name}” and its 12 files. This can't be undone."
- **Buttons:** "Cancel" (secondary) + "Delete project" (danger, names the action).
- **Never** use vague "Are you sure?" with "OK" / "Cancel" only.

---

## 8. Microcopy Checklist (apply to every screen)

- [ ] Every empty state has a next action, not just "nothing here".
- [ ] Every error says what happened + why + how to fix.
- [ ] Every loading state names what's loading.
- [ ] Every button label is a verb + object ("Create project"), never just "Submit" / "OK".
- [ ] No "Lorem ipsum", "TBD", "Coming soon", or generic triads anywhere.
- [ ] No raw error codes or stack traces shown to users.
- [ ] Paywall copy names the concrete feature delta.
